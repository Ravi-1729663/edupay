# Mandatory AI Usage Report

## AI TOOL USED

**ChatGPT, Claude, Gemini, and Z.ai — primarily used through the Antigravity development environment**

I used multiple AI development assistants during the EduPay implementation. Their roles were complementary: architecture and design reasoning, implementation assistance, code review/debugging, test generation, documentation, and validation.

I did not treat generated code as automatically correct. Important backend, database, financial, authorization, concurrency, and reconciliation behaviour was reviewed and validated through execution and automated tests.

## WHAT I ASKED AI TO DO

### 1. Architecture, Domain Design & Financial Integrity

I asked AI to design the system as a financial-grade fee collection and reconciliation platform rather than a basic CRUD application.

The AI was instructed to define and implement:

* Modular-monolith architecture
* FastAPI + SQLAlchemy + Alembic + PostgreSQL backend
* Next.js + TypeScript + Tailwind frontend
* Financial domain entities and relationships
* Fee heads, fee structures, concessions, installments, payments, allocations, reversals, reconciliation records, and audit logs
* PostgreSQL `NUMERIC(12,2)` for monetary values
* Immutable successful financial transactions
* Derived outstanding balances
* Database-level idempotency
* Backend-enforced RBAC
* Explicit payment state transitions
* Financial integrity validation

A major objective was to make the system resistant to real-world financial failure scenarios rather than only demonstrate successful payment flows.

# PROMPT THAT WAS MOST USEFUL

The most useful prompt was the structured senior-engineering implementation prompt that defined the system's non-negotiable financial invariants, architecture, failure scenarios, testing requirements, and acceptance criteria.

A representative section was:

> "Money = PostgreSQL NUMERIC(12,2). Floats are forbidden."

> "Financial records are IMMUTABLE. Corrections happen via linked reversal entries; nothing is edited or deleted after it becomes SUCCESS."

> "Idempotency enforced by DB unique constraint, never service-check only."

> "Authorization lives in the backend. Frontend hiding is UX, not security."

> "Every state transition writes an audit row."

The prompt also required genuine concurrency validation rather than simulated sequential testing:

> "true concurrent duplicate callback — two threads hit the callback endpoint simultaneously, assert exactly one financial record"

It also required an integrity checker and explicit acceptance criteria before progressing to the next implementation stage.

This prompt was particularly useful because it constrained the AI around **financial correctness, database integrity, failure handling, and testable acceptance criteria**, instead of simply asking it to generate application code.

# CODE I MODIFIED: What part?

I reviewed and modified AI-generated implementation where execution exposed issues or where the generated implementation needed to conform more precisely to the assessment requirements.

Important modifications included:

### 1. Alembic Test Configuration

I modified `conftest.py` to resolve the Alembic migration directory using an absolute path derived from the repository structure.

This removed dependence on the shell's current working directory.

### 2. Cross-Platform Frontend Build

I modified the frontend build configuration to replace Unix-specific file-copy commands with Node.js filesystem operations so the project could be executed reliably on Windows as well as Linux/macOS.

### 3. API Proxy / Local Development

I modified the frontend API integration to use a Next.js server-side proxy where appropriate, reducing local browser CORS/preflight issues during evaluation.

### 4. Financial Workflow Validation

I reviewed generated payment, allocation, reversal, reconciliation, and integrity logic against the defined financial invariants and acceptance criteria.

### 5. Testing and Fixtures

I adjusted test configuration and fixtures where necessary so migrations, seeded data, authentication, and integration tests could be executed from the repository root.

# AI OUTPUT THAT WAS WRONG

A concrete issue identified during implementation was the initial Alembic configuration generated for the Pytest environment.

The generated configuration used a relative migration path:

```text
script_location = alembic
```

This assumed that tests would always be executed from the backend directory.

However, the documented evaluation command executes tests from the repository root:

```text
pytest backend/app/tests
```

Under that execution context, Alembic could not resolve the migration directory.

This caused test setup failures even though the migration itself was valid.

---

# HOW I IDENTIFIED THE PROBLEM

I did not identify the issue by code inspection alone.

I executed the complete test suite from the repository root:

```text
pytest backend/app/tests
```

The test setup failed with an Alembic path-resolution error indicating that the configured migration directory could not be found.

This showed that the implementation was dependent on the process working directory.

I then traced the failure through the Pytest fixture and Alembic configuration.

---

# HOW I FIXED IT

I changed the configuration to derive the backend directory from the physical location of `conftest.py` and explicitly configure Alembic with the absolute migration path.

Conceptually, the fix changed the configuration from a working-directory-dependent path to a repository-location-dependent path.

After applying the fix, I reran the complete test suite from the repository root.

The final validation result was:

**50/50 Pytest tests passing.**

The tests covered authentication/RBAC, financial constraints, payment state transitions, idempotency, concurrent callbacks, allocation rules, reconciliation behaviour, reversal protection, and integrity validation.

# AI ASSISTANCE & HUMAN VALIDATION

AI was used as an engineering accelerator, not as a substitute for validation.

The implementation workflow was:

**Requirement → AI-assisted design → generated implementation → execution → test failure/validation → investigation → code modification → retest**

Particular attention was given to financial operations because generated code can appear logically correct while still failing under concurrency, database constraints, invalid state transitions, or unexpected payment states.

The final implementation was therefore validated through actual application execution, database migrations, seeded data, automated tests, and end-to-end workflow checks.
